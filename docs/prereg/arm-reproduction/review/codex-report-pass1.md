## 3. Vérificateur : écarts à la règle et cas limites

### V1 — BLOQUANT : les types de summary peuvent contourner l’exactitude

`docs/prereg/arm-reproduction/check_arm_repro.py:75` choisit la branche flottante dès qu’un seul côté est float ; le contrôle de type de la ligne 82 n’est alors jamais appliqué. `float_diff()` (`docs/prereg/arm-reproduction/check_arm_repro.py:52`) assimile un booléen à un nombre égal. Cela contredit `docs/prereg/arm-reproduction/protocol.md:114` et `docs/prereg/arm-reproduction/protocol.md:125`, qui exigent l’exactitude des entiers et booléens.

Contre-exemples exécutés avec le vrai summary confirmatory : remplacer le premier seed 0 (`data/nh01_confirmatory/summary.json:8`) par `5e-13` donne **REPRODUCED** ; remplacer `verdict/C2_unimodal/finite_optimum: true` (`data/nh01_confirmatory/summary.json:2211`) par `1.0` donne aussi **REPRODUCED**. Un diagnostic cellulaire `c_fro: 1.0` remplacé par `true` est également accepté (`docs/prereg/arm-reproduction/check_arm_repro.py:115`). Ce ne sont pas des tolérances numériques légitimes sur des champs entiers ou booléens.

Avant gel : valider le schéma et les types à partir des champs attendus, avant tout calcul de distance ; exclure explicitement bool des nombres. Le fait que les runners normaux ne produisent pas ces corruptions ne rend pas le validateur conforme à sa règle.

### V2 — MAJEUR : exactitude des clés incohérente avec celle des valeurs

Les clés sont des tuples de valeurs Python (`docs/prereg/arm-reproduction/check_arm_repro.py:38`, `docs/prereg/arm-reproduction/check_arm_repro.py:103`) : `1000 == 1000.0`, `1 == True`. Une cellule authentique de seed 1 devient seed `true` sans perdre **REPRODUCED** ; N = 1000.0 est accepté. Les champs de clé sont ensuite exclus du contrôle des valeurs (`docs/prereg/arm-reproduction/check_arm_repro.py:111`). À l’inverse, `n_probes: 32` → `32.0` est rejeté par la comparaison des représentations JSON (`docs/prereg/arm-reproduction/check_arm_repro.py:123`).

L’égalité mathématique int/float pour une clé numérique peut être un choix, mais elle doit être écrite ; un booléen comme seed doit être invalide. Avec les mêmes runners et sérialiseurs les types restent stables : le second cas n’est donc pas un échec ARM établi. Il montre que « exact » signifie trois choses différentes selon le champ.

### V3 — BLOQUANT : « no result » n’est pas implémenté et n’a pas de priorité définie

La section 6 classe un run incomplet comme **no result**, avec un redémarrage autorisé (`docs/prereg/arm-reproduction/protocol.md:128`). Le script n’a que trois verdicts (`docs/prereg/arm-reproduction/check_arm_repro.py:132`) et traite une cellule manquante comme **NOT_REPRODUCED** (`docs/prereg/arm-reproduction/check_arm_repro.py:127`) ; fichier absent/invalide : code 3 sans rapport JSON (`docs/prereg/arm-reproduction/check_arm_repro.py:99`). Contre-exemple exécuté : référence d’une cellule, rerun vide avec summary lisible → code 2, **NOT_REPRODUCED**, et non no result.

Ce n’est pas une possibilité abstraite : les runners possèdent un plafond mural de 8 h / 12 h (`code/experiments/nh01_hopfield_dream/confirmatory.py:48`, `code/experiments/nh01_hopfield_dream/correlated.py:45`) ; ils interrompent le pool et continuent vers analyse/écriture après dépassement (`code/experiments/nh01_hopfield_dream/confirmatory.py:349`, `code/experiments/nh01_hopfield_dream/correlated.py:211`). Une sortie 0 n’est donc pas à elle seule une preuve de complétude. Le nombre de tâches/cellules et la grille doivent être validés avant l’adjudication.

La règle de l’étude « worse of the two outcomes » (`docs/prereg/arm-reproduction/protocol.md:130`) ne précise ni la position de no result ni le cas mixte échec numérique / absence de résultat ; aucun agrégateur n’est fourni. Avant gel : établir une étape de validité/complétude et une table d’agrégation explicites ; conserver les deux résultats séparés. Un contrôle de complétude externe sous `docs/` suffit, sans modifier les runners gelés.

### V4 — MAJEUR : run_meta n’est pas réellement retiré avant de comparer

Le jeu de clés des dictionnaires est comparé avant l’exclusion (`docs/prereg/arm-reproduction/check_arm_repro.py:64`, `docs/prereg/arm-reproduction/check_arm_repro.py:67`). Modifier le contenu de `run_meta` est bien ignoré ; enlever uniquement ce membre d’un summary déclenche **NOT_REPRODUCED**, contrairement à « summary.json without run_meta » (`docs/prereg/arm-reproduction/protocol.md:114`). Cas exécuté. Les runners normaux ajoutent ce membre (`code/experiments/nh01_hopfield_dream/confirmatory.py:376`, `code/experiments/nh01_hopfield_dream/correlated.py:228`), donc le problème concerne surtout les exports/nettoyages de métadonnées. Filtrer le membre avant la comparaison des clés. L’exclusion ne vaut qu’au niveau racine, contrairement au comparateur historique récursif (`code/scripts/compare_nh01.py:26`) ; aucun run_meta imbriqué n’a été trouvé dans les summaries actuels.

### V5 — MAJEUR : validation de schéma et identité de la référence insuffisantes

`load_cells()` ne requiert aucun champ (`docs/prereg/arm-reproduction/check_arm_repro.py:38`) et ne vérifie pas que la ligne est un objet. Un champ absent d’un seul côté est détecté (`docs/prereg/arm-reproduction/check_arm_repro.py:112`), mais un champ requis absent des deux côtés est accepté. Deux entrées vides et deux summaries `{}` donnent **REPRODUCED**. Une clé non hachable ou une ligne `null` provoquent un `TypeError` non intercepté ; le code 3 « input error » n’est pas garanti (`docs/prereg/arm-reproduction/check_arm_repro.py:99`). `json.loads` accepte aussi les membres JSON répétés en conservant le dernier, sans détection (`docs/prereg/arm-reproduction/check_arm_repro.py:37`, `docs/prereg/arm-reproduction/check_arm_repro.py:97`).

Ces faux succès avec deux références dégradées ne se produisent pas contre les fichiers intacts vérifiés ici : cette limite est conditionnelle. La section 3 réclame une référence gelée (`docs/prereg/arm-reproduction/protocol.md:86`), mais le script n’en vérifie pas les hashes et les commandes de section 7 ne matérialisent pas ce contrôle. Avant gel : manifeste de référence exécuté, champs requis par run (ancestor_m absent en confirmatory, présent en correlated), grille attendue, types, dictionnaires JSON sans membres répétés et traitement propre des entrées invalides. Le contrôle de nombre doit porter sur les lignes et les clés uniques ; les doublons restent invalides.

### V6 — MAJEUR : NaN autorisés, infinis et valeurs invalides ne sont pas spécifiés

La gestion NaN/NaN et NaN/nombre des diagnostics est correcte (`docs/prereg/arm-reproduction/check_arm_repro.py:50`). Dans les données, seuls les `c_spec` dream/shrink sont NaN : 8 640 confirmatory, 28 080 correlated. C’est intentionnel : `spectral=False` (`code/experiments/nh01_hopfield_dream/confirmatory.py:57`, `code/experiments/nh01_hopfield_dream/correlated.py:56`) et `code/experiments/nh01_hopfield_dream/run.py:119` ; les lignes Hebb ont `c_spec=1.0` (`code/experiments/nh01_hopfield_dream/run.py:291`). Les ratios de summary peuvent aussi être NaN quand la capacité Hebb est zéro (`code/experiments/nh01_hopfield_dream/run.py:424`).

En revanche, +inf/+inf est accepté avec une différence annoncée nulle (`docs/prereg/arm-reproduction/check_arm_repro.py:56`) ; inf/valeur finie et inf de signes opposés sont rejetés, mais rangés dans `nan_pattern_mismatch`. Les mêmes chaînes ou `null` sont acceptés comme diagnostics si présents des deux côtés (`docs/prereg/arm-reproduction/check_arm_repro.py:54`). Aucun inf n’a été trouvé dans les cellules lues. La section 6 ne dit pas si un inf identique est valide ni où NaN est admissible (`docs/prereg/arm-reproduction/protocol.md:125`). Avant gel : décider finitude, sentinelles autorisées par champ et cas invalides ; ne pas masquer une entrée numérique non valide sous « différence 0 ».

### V7 — MINEUR : seuils CLI non validés et diagnostics peu localisables

`--strict` et `--band` acceptent NaN, inf, valeurs négatives et un ordre inversé (`docs/prereg/arm-reproduction/check_arm_repro.py:91`). Démonstrations : `--strict nan` produit **INCONCLUSIVE_FLOAT** même pour des entrées identiques ; `--strict inf` produit **REPRODUCED** pour une différence d’énergie ≈ 99.5. Les commandes normales n’utilisent pas ces options, ce qui réduit le risque, mais un seuil gelé doit être fini et respecter 0 ≤ strict ≤ band, avec toute dérogation explicite.

Les rapports ne donnent pas d’exemples de clés manquantes, ni la clé de cellule au maximum d’un diagnostic (`docs/prereg/arm-reproduction/check_arm_repro.py:102`, `docs/prereg/arm-reproduction/check_arm_repro.py:118`). Le parcours de sets rend en outre l’attribution d’un maximum de summary ex æquo variable (`docs/prereg/arm-reproduction/check_arm_repro.py:66`). Verdict stable dans les cas ordinaires ; audit d’un échec inutilement difficile.

### V8 — OK : ordre et doublons de cellules ; réserves sur les autres ordres

Le script ignore correctement l’ordre des lignes et des membres d’une cellule ; les deux permutations ont été testées avec succès (`docs/prereg/arm-reproduction/check_arm_repro.py:38`, `docs/prereg/arm-reproduction/check_arm_repro.py:109`). Cela convient à `imap_unordered` (`code/experiments/nh01_hopfield_dream/confirmatory.py:341`, `code/experiments/nh01_hopfield_dream/correlated.py:205`). Contrairement à ce script, le comparateur historique écrase les doublons sans les signaler (`code/scripts/compare_nh01.py:22`).

L’ordre des dictionnaires de summary est ignoré, celui des listes est comparé position par position (`docs/prereg/arm-reproduction/check_arm_repro.py:70`) : approprié aux seeds triés par `code/experiments/nh01_hopfield_dream/run.py:408` et aux intervalles ordonnés. ## 5. Protocole, commandes et risques aarch64

### P1 — BLOQUANT : environnement pas encore exécutable et interpréteur non sélectionné

Le lock mentionné à `docs/prereg/arm-reproduction/protocol.md:50` n’existe pas dans ce commit ; la commande `docs/prereg/arm-reproduction/protocol.md:142` échoue donc telle quelle. C’est annoncé comme travail L0 restant (`docs/prereg/arm-reproduction/protocol.md:194`), pas une incohérence cachée, mais cela empêche le gel. Le lock doit contenir **toutes** les exigences et dépendances transitives épinglées et hashées ; `pip --require-hashes` est syntaxiquement correct, il n’invente pas les hashes manquants. La [documentation pip](https://pip.pypa.io/en/stable/topics/secure-installs/) confirme ces exigences et distingue le verrouillage par hash de l’interdiction des sources.

L’interpréteur de TBD-4 est une archive autonome, pas une exigence pip (`docs/prereg/arm-reproduction/protocol.md:58`). Aucun URL/version de build/nom de fichier/hash/chemin d’installation n’est fourni ; `python3.12 -m venv` (`docs/prereg/arm-reproduction/protocol.md:141`) choisira le binaire du PATH, éventuellement celui du système et non le 3.12.15 proposé. `python -VV` affiche mais n’impose aucune version. `run.sh` affiche également une version « expected » sans la vérifier et peut utiliser la variable héritée `PYTHON` (`code/run.sh:38`, `code/run.sh:46`).

Avant gel : séparer le verrou de l’interpréteur du lock pip ; nommer son exécutable absolu, vérifier architecture et version, fixer les wheels exactes (éviter une résolution vers sdist), puis valider la fermeture des dépendances. Ne pas remplacer silencieusement une version faute de wheel : déviation ou amendement préalable.

### P2 — MAJEUR : BLAS enregistré après choix, mais pas encore effectivement fixé

`docs/prereg/arm-reproduction/protocol.md:77` désigne « le BLAS de la wheel » sans nommer l’artefact qui le contient ; le nom et la version ne seraient consignés qu’avant le run. Une fois la wheel exacte hashée, son contenu BLAS devient fixé : c’est suffisant pour ce volet, sans exiger le même binaire qu’en x86. En l’état il reste à l’établir. Le freeze historique donne les packages, pas la wheel x86 ni son BLAS ; l’affirmation d’une provenance PyPI sur le serveur (`docs/prereg/arm-reproduction/protocol.md:78`) est **invérifiable à partir des pièces fournies**.

`code/run.sh:42` fixe correctement les quatre variables de threads pour ses enfants. Le pytest et le probe sont des processus distincts exécutés avant ce wrapper ; le pytest n’a aucune limite de threads et le probe n’en fixe que deux (`docs/prereg/arm-reproduction/protocol.md:145`, `docs/prereg/arm-reproduction/protocol.md:146`). Avec un OpenBLAS standard ces deux variables sont pertinentes, mais l’environnement annoncé « un seul thread fixé » doit s’appliquer avant tous les imports/tests/probes. `show_config()` renseigne la construction ; contrôler aussi les bibliothèques effectivement chargées, le backend actif et le nombre effectif de threads. Archiver ces observations ainsi que les hashes des binaires sélectionnés et l’absence de préchargement alternatif.

### P3 — BLOQUANT : redémarrage et gzip peuvent valider un ancien résultat

`run.sh` n’offre pas de paramètre de répertoire de sortie ; ses chemins sont codés en dur (`code/run.sh:56`). La section 6 exige pourtant un redémarrage « from scratch in a new results directory » (`docs/prereg/arm-reproduction/protocol.md:128`). Il faut écrire comment le faire sans modifier `code/` : archiver/déplacer le répertoire complet entre tentatives, ou lancer le même module avec `--out` vers une tentative neuve et tracer cette commande.

Le cas dangereux suit directement des commandes `docs/prereg/arm-reproduction/protocol.md:148` et `docs/prereg/arm-reproduction/protocol.md:150` : le runner réécrit `cells.jsonl` mais ne supprime pas un ancien `cells.jsonl.gz` (`code/experiments/nh01_hopfield_dream/confirmatory.py:354`, `code/experiments/nh01_hopfield_dream/correlated.py:204`). `gzip -k` refuse d’écraser une archive existante ; les deux comparateurs ne lisent que l’archive (`docs/prereg/arm-reproduction/check_arm_repro.py:95`, `code/scripts/compare_nh01.py:37`). Démonstration exécutée : archive conforme préexistante, nouveau plaintext avec retrieved_frac modifié, gzip code 1 « already exists -- skipping », vérificateur ensuite **REPRODUCED** sur l’ancien gzip. Avec summary inchangé et une modification de diagnostic seulement, le même risque existe sans incohérence de summary.

Sur un premier passage réellement neuf, la commande est correcte. Avant gel : imposer des chemins de tentative uniques, vérifier leur absence initiale, arrêter sur échec de compression et prouver que l’archive correspond au plaintext de cette tentative. Ne pas compter sur une réexécution manuelle des mêmes lignes.

### P4 — MAJEUR : l’enchaînement ne formalise ni l’arrêt ni les codes attendus

Les lignes `docs/prereg/arm-reproduction/protocol.md:141` à `docs/prereg/arm-reproduction/protocol.md:154` n’ont pas de garde globale. Exécutées dans un shell ordinaire, un échec pip/pytest/probe/run/gzip n’empêche pas les lignes suivantes, malgré la consigne d’arrêt de `docs/prereg/arm-reproduction/protocol.md:160`. La protection `set -euo pipefail` interne de `code/run.sh:33` ne s’applique pas au shell appelant.

Inversement, appliquer naïvement `set -e` à toute la recette arrêterait la boucle au premier résultat valide **INCONCLUSIVE_FLOAT** (code 1) ou **NOT_REPRODUCED** (code 2), empêchant de comparer l’autre run (`docs/prereg/arm-reproduction/check_arm_repro.py:11`). Il faut un wrapper sous `docs/` ou des instructions explicites qui arrêtent sur erreur technique, capturent volontairement 0/1/2 comme verdicts, et enregistrent aussi 3 et les exceptions. Il faut consigner les vrais codes des runners et les sorties standard/erreur : les relevés de version/hôte ne sont actuellement qu’imprimés, pas archivés par les commandes.

### P5 — MAJEUR : budget d’accès et caps des runners peuvent se contredire

Le lancement conditionné à une fin ≥ 2 h avant la fin des 24 h (`docs/prereg/arm-reproduction/protocol.md:187`) ne vérifie pas les caps de 8 h/12 h gelés dans les runners. À s = 0.5, le tableau extrapole environ 3.9 h et 12.7 h : cela peut tenir dans les 22 h disponibles tout en déclenchant le plafond correlated. Les caps sont testés après réception d’une tâche, pas comme une interruption stricte à la seconde (`code/experiments/nh01_hopfield_dream/confirmatory.py:349`, `code/experiments/nh01_hopfield_dream/correlated.py:211`).

Le seul probe lancé est confirmatory, à deux charges, seed 999 (`docs/prereg/arm-reproduction/protocol.md:146`, `code/experiments/nh01_hopfield_dream/confirmatory.py:316`). Le probe correlated existe et cible m = 0.30 (`code/experiments/nh01_hopfield_dream/correlated.py:185`), mais n’est pas utilisé. Le s calculé à partir de 2 420 s est une approximation cohérente de la moyenne confirmatory, pas une validation de tout le régime correlated. Avant gel : arrêter une procédure de budget tenant compte des deux caps, de la contention et des coûts hors calcul ; préciser le traitement d’un accès insuffisant sans modification opportuniste des workers/seeds.

### P6 — MINEUR : série et concurrence sont deux recettes différentes

Les commandes écrites lancent confirmatory puis correlated en série (`docs/prereg/arm-reproduction/protocol.md:148`), soit environ 8.28 h à s = 1 pour les cellules. Le tableau « both, concurrent » annonce 6.4 h (`docs/prereg/arm-reproduction/protocol.md:182`), et le texte autorise ensuite les deux modes (`docs/prereg/arm-reproduction/protocol.md:157`), sans commande concurrente, attente des deux PID ou listes de CPU. Les workers ont le bon nombre et ne changent pas le plan ; le budget et la mesure de vitesse doivent néanmoins citer le mode réellement utilisé. Une affinité disjointe réduit la contention CPU, mais n’isole pas mémoire/puissance ; l’hypothèse « cela change seulement les durées » (`docs/prereg/arm-reproduction/protocol.md:44`) reste conditionnelle à une exécution complète.

### P7 — MAJEUR : pages 64 Ko et liaison des extensions à valider avant les calculs

Les tags cp312/manylinux/aarch64 valident une ABI et une famille de plateforme, pas l’aptitude de chaque ELF à se charger sur un noyau à pages 64 Ko (`docs/prereg/arm-reproduction/protocol.md:56`, `docs/prereg/arm-reproduction/protocol.md:144`, `../stack.md:73`). Il faut valider l’archive CPython et les extensions natives réellement choisies (NumPy, BLAS/LAPACK, Matplotlib, contourpy, etc.), leurs dépendances et l’alignement des segments ELF ; un import réel et une petite opération linalg sur la cible sont nécessaires. Les tests du dépôt constituent ensuite un contrôle utile, sans prouver tout N = 1 000. Le protocole relève seulement la taille de page, sans critère explicite d’acceptation de la chaîne binaire.

Le [guide NVIDIA sur les pages](https://docs.nvidia.com/dgx/dgx-station-development-guide/porting/pagesize.html) confirme le contexte 64 Ko et l’absence de support annoncé pour les applications exigeant 4 Ko. Il ne permet pas de conclure que les wheels ici échoueront. Verdict sur leur chargement : **invérifiable avant essai/inspection de ces artefacts**, à documenter comme échec d’environnement, pas comme non-reproduction scientifique. Aucun changement de noyau ou compilation locale improvisée ne doit être absorbé silencieusement dans l’environnement gelé.

### P8 — MAJEUR : une graine et un thread ne garantissent pas l’identité cross-ISA

La chaîne numérique sensible existe bien dans le runner : produit matriciel Hebb, `np.linalg.eigh`, clipping des petites valeurs propres négatives puis reconstruction spectrale (`code/experiments/nh01_hopfield_dream/run.py:285`, `code/experiments/nh01_hopfield_dream/run.py:288`, `code/experiments/nh01_hopfield_dream/run.py:295`). NumPy indique que [eigh utilise LAPACK _syevd/_heevd](https://numpy.org/doc/stable/reference/generated/numpy.linalg.eigh.html). L’architecture, la build LAPACK/BLAS, la réduction et les instructions vectorielles peuvent donc affecter les derniers bits, même avec un thread.

Le changement de signe isolé d’un vecteur propre s’annule dans `(v * wt) @ v.T` ; ce n’est pas à lui seul un motif de divergence. Les arrondis des valeurs propres/vecteurs, le clipping et les contractions restent pertinents. Les états peuvent ensuite diverger au voisinage des comparaisons `h > tol`, `u < p_up` ou du seuil de retrieval (`code/experiments/nh01_hopfield_dream/run.py:185`, `code/experiments/nh01_hopfield_dream/run.py:219`, `code/experiments/nh01_hopfield_dream/run.py:246`). La tolérance TIE_REL = 1e-12 (`code/experiments/nh01_hopfield_dream/run.py:53`) est une règle interne à la dynamique, distincte de la tolérance absolue sur les diagnostics.

La [politique RNG NumPy](https://numpy.org/doc/stable/reference/random/compatibility.html) ne promet pas la compatibilité intégrale des streams entre machines/builds. Cela n’établit pas une divergence pour les méthodes concrètement utilisées ici ; un court témoin hashé des streams et des entrées est utile pour localiser un éventuel échec sans relancer ni ajuster le protocole. Une différence discrète restera **NOT_REPRODUCED au sens du critère fixé**, même si elle provient d’une bifurcation numérique légitime ; ne pas en déduire automatiquement une réfutation du résultat scientifique.

### P9 — MINEUR : figure non probante, mais actuellement obligatoire pour terminer la recette

L’identité de `figure.png` est correctement exclue de la règle (`docs/prereg/arm-reproduction/protocol.md:131`). Le comparateur historique exige néanmoins que le fichier existe pour calculer son hash (`code/scripts/compare_nh01.py:71`) ; absence testée → `FileNotFoundError`. Les runners calculent summary avant la figure (`code/experiments/nh01_hopfield_dream/confirmatory.py:377`, `code/experiments/nh01_hopfield_dream/correlated.py:229`), donc une panne de rendu peut laisser des artefacts numériques complets avec une commande en échec. La consigne « crash = no result » est actuellement plus exigeante que « identité de figure non requise », sans contradiction logique stricte. PI doit préciser si un échec exclusivement graphique invalide le run ou permet une comparaison numérique avec annotation. Le vérificateur décisionnel, lui, ne lit pas la figure.

### P10 — MINEUR : provenance et gel à rendre exécutables

La section 3 mentionne les bons contrôles (`docs/prereg/arm-reproduction/protocol.md:88`), mais le manifeste de code ne couvre que quatre modules (`code/CODE_SHA256_AT_TAG.txt:1`), pas `run.sh`, tests, comparateurs ni exigences. Le diff Git complète ce contrôle ; les chemins du manifeste sont relatifs à `code/`. Pour les données, exécuter aussi `data/MANIFEST.sha256` depuis `data/` (`data/README.md:5`). Les conditions avant/après doivent porter sur les contenus gelés, pas seulement sur un arbre Git « propre », puisque venv/results sont des sorties locales attendues.

Le gel proposé cite trois fichiers et SWH (`docs/prereg/arm-reproduction/protocol.md:192`), mais aucun manifeste de l’ensemble, hash de l’interpréteur, identité complète des wheels et engagement des fichiers de référence n’est encore concret. Préparer cela avant le gel, puis enregistrer tag annoté, commit, empreintes et SWHID de révision. Cette recommandation suit aussi le skill `hypneum-prereg` consulté pour la revue ; elle ne constitue pas une demande d’autorisation ni une modification du dépôt.

L’archive distante et sa vérification (`docs/prereg/arm-reproduction/protocol.md:197`) sont une bonne intention ; il manque la recette de capture des logs/versions, les chemins propres par tentative, les dates UTC et les codes de sortie. Les métadonnées des runners ne capturent pas les variables de threads ou l’affinité (`code/experiments/nh01_hopfield_dream/confirmatory.py:357`, `code/experiments/nh01_hopfield_dream/correlated.py:215`). L’accès réseau, le chemin d’archive et le SWHID futur restent invérifiables.

La fiche mentionne aussi le partage de puissance (`../stack.md:76`), confirmé par le [guide NVIDIA](https://docs.nvidia.com/dgx/dgx-station-development-guide/dynamic-power-sloshing.html). L’amplitude de son effet sur NH-01 n’est pas mesurée ; il justifie de documenter la coactivité et de présenter s comme une vitesse observée dans cette session, pas une propriété générale de Grace.

## 6. Bande inconclusive, portée des conclusions et décisions avant gel

### I1 — MAJEUR : vocabulaire « bit level » impropre ; règle numérique néanmoins défendable

`docs/prereg/arm-reproduction/protocol.md:125` admet déjà des différences jusqu’à 1e-12 : même **REPRODUCED** ne signifie pas identité bit à bit. Le terme « INCONCLUSIVE (bit level) » (`docs/prereg/arm-reproduction/protocol.md:126`) devrait signifier « critère strict à 1e-12 non établi, diagnostic dans la bande », sans revendication de bit-exactitude. L’usage de distances absolues par scalaire est une lecture possible du README, pas une norme déjà écrite par lui (`README.md:105`). TBD-2 la soumet correctement à décision.

Les bornes par défaut, pour entrées valides et schéma stabilisé, implémentent bien ≤ 1e-12, puis (1e-12, 1e-9], puis > 1e-9 (`docs/prereg/arm-reproduction/check_arm_repro.py:132`). Tests à environ 5e-13, 5e-10 et 2e-9 : respectivement 0/REPRODUCED, 1/INCONCLUSIVE_FLOAT, 2/NOT_REPRODUCED. Le maximum porte à la fois sur cellules et summary (`docs/prereg/arm-reproduction/check_arm_repro.py:130`). Aucun test statistique nouveau n’est nécessaire pour comparer déterministiquement ces artefacts ; 1e-9 n’est pas une marge d’équivalence scientifique estimée.

L’interprétation demandée — résultats discrets identiques et labels identiques, diagnostics dans la bande : affirmations conservées — est cohérente pour les statistiques issues des mêmes comptes, à condition de corriger V1/V2 et de préciser les choix de grille du summary. Au-delà de 1e-9, le texte doit distinguer « critère numérique non satisfait » de « affirmation réfutée », même si tous les résultats discrets restent identiques. ### I2 — MAJEUR : « claims stand » doit conserver les réserves déjà présentes

Les résultats correlated archivés portent des labels automatiques dont le dépôt donne une réserve explicite pour m = 0.30 : contrôle censuré à T = 0.2, appréciation post-analyse inconclusive (`data/README.md:22`). Le tableau descriptif peut être fixé avant run (`docs/prereg/arm-reproduction/protocol.md:132`) ; il ne doit pas modifier le verdict numérique.
